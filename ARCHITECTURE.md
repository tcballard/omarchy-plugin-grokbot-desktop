# Architecture

`Main.qml` is a `kind: service` entry point. It runs inside the long-running `omarchy-shell` Quickshell process and mounts one transparent `PanelWindow` per output on `WlrLayershell`. A layer surface stays on the output it first mapped to, so each output has its own window and only the one named by `monitor` is shown. A drag that crosses the edge keeps going when the cursor helper can see the left button: the press is cancelled by the compositor at the boundary, and `bin/grokbot-cursor` then supplies the position plus the left-button release (BTN_LEFT only, from mouse event nodes, never grabbed). Reading `/dev/input/event*` normally needs membership of the `input` group. When the helper reports `buttons 0`, or has not reported at all, the cancelled press ends the drag at the edge, since no release would ever arrive (`qml/pointer.js`, `cancelEndsDrag`). The drop writes `monitor`, `marginX`, and `marginY` as integers onto the existing shell entry and does not rewrite the rest of that entry. The mark uses those same integers, so a later start puts it back on that output. The mark is placed with `marginX` and `marginY` from the corner named by `anchor` (`br`, `bl`, `tr`, or `tl`). The window always covers the whole output and never changes size or anchors. An earlier version shrank it to a box around the mark while idle, but Hyprland re-places a layer surface that grows or shrinks, so the mark visibly jumped toward the middle of the screen whenever the card opened or closed. The cost is that motion redraws the whole output's surface: in Calm, the default, that only happens while the eyes follow the pointer, while Playful and Hyper breathe continuously. Before the window first maps, the companion adds a runtime layer rule (`hyprctl eval`, `hl.layer_rule` with `no_anim` for the `grokbot-desktop` namespace), the same rule Omarchy's `apps/omarchy-shell.lua` gives its own shell surfaces, so it is not popped in from the middle of the screen when shown; it adds the rule again after each `configreloaded` event, and shows the window when that call returns or after 1.5s. The window is hidden while Omarchy's screensaver runs (`org.omarchy.screensaver`: a full-screen terminal window in older Omarchy, which the companion's top layer would otherwise draw over, and a native overlay-layer surface since 27 October 2026), tracked from Hyprland's `openwindow`/`closewindow` and `openlayer`/`closelayer` events, with a 20-second `hyprctl` check while hidden in case a close event is missed. A `mask` limits pointer input to the mark and, while it is open, the bubble card (chat and appearance pages). The rest of the desktop stays clickable with the bubble open; the minimize button, Esc, a click on the mark, or `dismiss` closes it. Only the right-click menu widens the mask to the output, so a click anywhere closes the menu.

Dodge mode, on by default, uses the cursor helper rather than the layer surface. When the pointer comes near the mark, it fades. Its input region stays active so clicks, drags and scrolling work immediately; hovering restores opacity. Outside the mark/card remains click-through. Calm motion keeps a slow breath and skips the float. Playful adds the float and the gaze spring. Hyper orbits and hops. Gaze spring frames run only while the eyes are catching up. Blink, ask, and named animations still run when they are triggered. Scrolling over the mark steps through the roster one bot per 120 units of wheel delta (`qml/pointer.js`, `wheelStep`), so a touchpad's small deltas add up first; a change of direction or a 400 ms pause resets the count. Hyprland window addresses are normalised there too, since socket events omit the `0x` that `hyprctl -j clients` includes.

`qml/shapes.js` stores Grok Bot's fourteen avatar shapes, measured from the app's own avatar picker by `tools/measure-avatars.py`: each outline (tilt included) resampled to the same point count, the two eye capsules for that shape, and the picker's pumpkin stem for the pebble. `morphProgress` can blend any shape into any other, eyes included. `qml/palette.js` stores the 11 named colours. `qml/theme.js` holds the chrome colours for the card, menu, and name tag. Text is set like Grok Bot's app, which uses Apple's SF Pro: SF Pro Text or SF Pro where installed, otherwise the bundled Inter (`assets/fonts`, SIL OFL 1.1, Regular and SemiBold subset to Latin, Greek and Cyrillic), the closest open match. Emphasis uses SemiBold rather than Bold, as the app does, which also keeps Qt from emboldening the SemiBold face. Without either font, the shell's `Style.font.family` applies. `CompanionMark.qml` draws the silhouette as a `QtQuick.Shapes` path (the curve renderer where Qt has it) and the eyes as two rotated rounded rectangles (`MarkEye.qml`), so the mark is drawn on the GPU and stays crisp at fractional scales; only a bot photo, when one is set, is clipped through a Canvas. `qml/face.js` sizes the two eye cut-outs: rounded rectangles that are tall capsules when open and flatten into lid lines when they blink or sleep. `omarchy` is not a swatch: the shell reads `accent` from the active theme `colors.toml`, with `Commons.Color` as the fallback, and crossfades it with the same morph.

`CompanionMark.qml` fills a flat silhouette. There is no outline and no highlight. The face is two capsules placed, sized, and tilted for each shape as Grok Bot draws them, leaning with their tops to the left. On the desktop they are cut through the shape (a `MultiEffect` inverted mask over supersampled, mipmapped layers), so the wallpaper shows through as it would through the app's avatar; in the bubble and appearance page they are painted in the colour of the surface behind (`#F4F4F5` on black). On the desktop the mark moves like a head, as Grok Bot moves Bob (measured from a 60fps recording of the app's chat header): facing the pointer's direction, the eyes travel about 0.4 of the body radius across and 0.3 up or down, shrink and narrow as the face turns away (they are largest and upright facing you), and the whole outline rolls up to 20 degrees with the turn. A pointer off a corner turns it fully both ways. Bob's picker pose is his look up and to the right. Each shape's face position, eye size, and how much of each look its eyes can take before reaching its edge come from a table in `qml/shapes.js` generated by `tools/look-table.mjs`. While an ask runs, the mark plays the app's measured "Working…" loop of looks and holds, each reached in about 280ms on a fast-out curve, with one blink. The picker, roster, and header marks keep the picker pose. They squash on a blink, and squint or open for think, happy, alert, and sleep. After two minutes without a cursor event the capsules become slits. An optional `avatarImage` on a roster bot is clipped to the mark when appearance is synced from that bot. Roster shapes such as `teardrop`, `blob`, `hex`, `tablet`, `wedge`, `squircle`, `pebble`, and `cloud` are the app's own names: Grok Bot's roster shows `blob` as the round shape and `pebble` as the lumpy round one, which its picker decorates with a pumpkin stem that avatars do not wear. The remaining shapes are named for how they look, and older names alias onto the nearest of the fourteen.

Speech-bubble and settings strings that come from the roster, the prompt, a reply, or IPC use `Text.PlainText`.

## Processes

These `Process` objects in `Main.qml` start with a cleared environment (`clearEnvironment: true`): `askProc` and `providerProc` (`bin/agent-desktop-ask` and `bin/agent-desktop-roster`, given `askEnvironment()`: a fixed `PATH`, Python isolation variables, and a list of locale, XDG, proxy, certificate and agent-credential variables copied when set), `syncProc` (HOME and XDG_CONFIG_HOME), `providerConfigProc` (HOME), `attachProc` and `cursorProc` (listed below). `dictateProc` (`bin/grokbot-dictate`) and `avatarBuilderProc` (`bin/agent-desktop-avatar`) run `/usr/bin/python3 -I` with the shell's environment. The `hyprctl` checks, the layer-rule call and the file chooser also inherit it.

All built-in agent adapters receive the composed prompt on stdin. Grok uses `--no-auto-update --prompt-file /dev/stdin`: its file reader consumes the pipe as plain text, with no named temporary file and no prompt in argv or the environment. Unsupported Grok versions fail without a command-line fallback. The upstream contract is [`HeadlessPrompt::from_file`](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-pager/src/headless/cli.rs#L58), which reads the path as UTF-8 and treats non-`.json` paths as text.

- `bin/grokbot-cursor` is `/usr/bin/python3 -I -S`. It may see only `HYPRLAND_INSTANCE_SIGNATURE` and `XDG_RUNTIME_DIR`, asks Hyprland for `cursorpos`, and prints `x y` when the position changes. At start it prints `buttons 1` when it could open at least one mouse event node and `buttons 0` when it could not. It also prints `down` or `up` when the combined left button changes, and no other input. It asks Hyprland at most 30 times a second while the pointer moves and 5 times a second for ten seconds after it stops; after that, once a second when event nodes are open (motion on them wakes it at once) and 5 times a second otherwise. It exits when its parent changes.
- `bin/grokbot-attach` is `/usr/bin/python3 -I` with only `XDG_RUNTIME_DIR`, `WAYLAND_DISPLAY`, and `HYPRLAND_INSTANCE_SIGNATURE`. `paste` reads a PNG, JPEG, WebP, or GIF image from `wl-paste`, and `file PATH...` copies files chosen in Omarchy's portal file chooser (`omarchy-file-select`, run by the shell; the card hides while it is open) or dropped on the card. Any regular file up to 25 MB is kept, under its name after a unique prefix, as a 0600 copy in `$XDG_RUNTIME_DIR/grokbot-desktop/attachments` (0700, cleared at logout, copies older than a day pruned), and each path is printed. The shell accepts only paths in that directory.
- `bin/agent-desktop-ask` is the desktop compatibility client for Provider API v1. It starts `bin/agent-desktop-provider --provider grokbot` over private pipes. The same client supports Hermes and the example adapter. GrokBot discovery, dispatch selection and callback correlation live behind `agent_desktop/grokbot.py`; QML no longer starts its transport directly. When the GrokBot worker fails, the adapter carries the worker's own stderr line into the fault message (control characters removed, at most 400 characters; a Python traceback or empty output falls back to a generic message for that exit code), and the client prints it, so the bubble says why. The client maps a completed event to the existing text result and a deferred event to exit 10, preserving the desktop's waiting-exchange/IPC reply handling. The existing picker now includes configured Hermes and example agents discovered by the same protocol. Grok IDs and settings retain their legacy names; other agents have provider-qualified desktop IDs.
- `bin/grokbot-ask` is the GrokBot adapter's per-ask transport worker, a thin wrapper around `agent_desktop/transport.py` that stays a separate process so the adapter can stop it and its agent's process group. It is launched with `/usr/bin/setpriv --pdeathsig TERM` then `/usr/bin/python3 -I`. Stdin is `{"askId","botId","botName","prompt","host","attachments"}`; up to four attachments are accepted, and only as files saved in the attachment directory. In agent mode the agent runs in that directory and the prompt names the files (Codex also gets `--image` for images); webhook mode refuses attachments. Webhook mode reads the bearer token from `~/.config/omarchy/grokbot-webhook.key` or `GROKBOT_WEBHOOK_KEY` and POSTs those four fields, with `askId` and the `replyWith` argument array and stdin instructions that answer it, plus the routine's own header when `webhookHeader` names one, with its value from `grokbot-webhook-header.key`. Connecting gets 10 seconds and the answer 45; a failure names its cause on stderr. A routine that only acknowledges the ask makes it exit 10, and the shell keeps the question waiting. Agent mode resolves `grok`, `claude`, `codex`, `opencode`, and the other Omarchy agent names from trusted directories, writes the prompt to that process's stdin, and stops at 64 KiB of stdout. The token and the prompt are not arguments.

`Component.onDestruction` stops both processes. Hiding the companion cancels an ask in flight. Closing the bubble, Esc, or a click outside it does not; the Stop button in the composer does. A prompt submitted while a stopped ask's process is still exiting is kept in `queuedPrompt` and sent once that process has exited, unless the bot on screen or the draft has changed meanwhile; after 5 seconds it is given up and the draft stays in the field. A reply that arrives while the bubble is closed, for any bot, leaves a dot on the mark until the bubble opens; a dot for a bot whose chip is folded away shows on the header pill (`unreadHidden`). Each bot keeps its own conversation and unsent draft in memory (`threads`, keyed by bot id; never saved). A conversation is its earlier exchanges (`history`, up to 40, oldest first) plus the latest in `askedText`, `bubbleBody`, and `noticeLinks`; a new ask or notice moves the latest into the history, and the bubble shows them all in one scrolling view that settles on the newest, or on the top of a reply too long to fit. Switching bots stashes the conversation on screen and restores the next bot's. Clearing a conversation (the right-click menu or `clear` over IPC) keeps it in `clearedThread` behind an Undo chip for 8 seconds; switching bots or a new ask lets it go. One ask runs at a time; it remembers the bot it was sent to (`askBotId`), and its reply is shown if that bot is on screen or otherwise kept with it and marked with a dot on its chip (`unreadBots`). The typing dots, stop button, and work loop follow `askingHere`, which is true only while the bot on screen is the one asking.

A webhook ask that the routine only acknowledges ends the ask but not the question: `awaiting` maps its `askId` to the bot and the time, and its exchange carries the same id as `wait` (`awaitingId` for the latest on screen) through the history, bot switches, clearing, and undo. `reply <askId|bot> <text>` over IPC, or a `say` titled with a waiting bot's name, fills that exchange wherever it now is (`answerWaiting`); with nothing to fill, the answer starts a new exchange in that bot's conversation. Either way an answer for a bot not on screen marks it unread. A question still waiting after ten minutes is answered with a note that the reply will be in Grok Bot. The dots and the work loop follow `busyHere`: asking, or waiting on screen.

`bin/grokbot-connect` is run by hand, not by the shell. It first loads and checks `grokbot-desktop.json`, and stops before prompting if that file is not a regular JSON object. It reads the Webhook URL and Sender key (without echo), sends one test ask through `bin/grokbot-ask` from a private temporary copy of the settings, and only then saves: the URL and webhook mode to `grokbot-desktop.json` first, keeping its other keys, then the key and any header value (0600, replaced atomically) where asks read them, `webhookKeyFile` and `webhookHeaderFile` when set. If any write fails, every file it touched is put back as it was.

The appearance page runs `bin/grokbot-sync --app` as an isolated Python child with only HOME and XDG_CONFIG_HOME. It reads Grok Bot's `sand-client-persistence` account-slot (schema 1) and that account's last-roster (schema 4); names are base32-encoded cache keys. It imports only profile fields, never credentials or conversation contents. Groups and removed rows are excluded. Missing, invalid, empty, duplicate, oversized, or unsupported data leaves the previous roster intact. A successful write goes to an exclusive temporary file in the same directory (`mkstemp`, fsync) and then replaces `~/.config/omarchy/grokbot-bots.json`, which the service watches and explicitly reloads. Profiles, seeds and settings are read with `O_NOFOLLOW` and a bounded read. `--from` still accepts a local agents directory. The cache schema is an app implementation detail; future changes fail with an actionable error.

A persistent, plain-text name badge sits below the mark, with space reserved inside the stage. It elides long names, stays within horizontal screen bounds, follows dodge opacity, and remains inside the companion stage input region.

The waveform button launches `bin/grokbot-dictate` (`/usr/bin/python3 -I`). It runs `omarchy dictation toggle` first, which follows `~/.config/omarchy/defaults/dictation`; then the backend named in that file, then Superwhisper (`superwhisper record`), Voxtype (`voxtype record toggle`) and Hex. Each is run as a child with a timeout, and the helper stops at the first that takes the toggle. It moves on only when an attempt certainly did nothing: the command is missing, it says it does not know the command (stable Omarchy has no `dictation`), Voxtype's toggle fails (its daemon is not running), or Hex cannot be started. Any other failure and every timeout end the attempt with an error, so a second recording is not started. With Hex it starts a recording and, on the next press, prints the transcript from `hex dictation stop --print` on stdout for the shell to insert. It does not take the transcript as an argument.

`qml/dictation.js` and `agent_desktop/wake.py` implement the same wake-phrase rules, and `tests/fixtures/wake-phrases.json` is run against both. `dictate` IPC and a prompt that starts with "Hey <name>" use the QML copy. Voxtype's `[output.post_process]` filter, `bin/grokbot-dictation-route --wtype` and `bin/grokbot-voice-watch` use the Python module, so a wake phrase is not typed into the focused window. The Python side matches against `GROKBOT_BOTS` when set, otherwise the synced `$XDG_CONFIG_HOME/omarchy/grokbot-bots.json`, then `~/.config/omarchy/grokbot-bots.json`, then the bundled `data/bots.json`. Text without a wake phrase is passed through whole (up to 1 MiB is held to decide; longer input is still copied through); only the first 4,000 characters of a wake line are routed. `bin/grokbot-voice-watch --enable` is the opt-in Superwhisper and Voxtype watcher. It is not started by the shell service.

For dictation, the router writes text to `bin/grokbot-desktop-ctl dictate` on stdin. The control helper first tries the daemon backend's control socket (below); when that directory or socket does not exist or refuses the connection, it connects directly to Omarchy's Unix socket, scoped to `OMARCHY_PATH/shell` and `WAYLAND_DISPLAY`, after checking the runtime directory, socket owner and peer UID. It sends a unit-separated request ending in a record separator; input containing those separators or NUL is refused. The plugin prefers `ShellIpc` (`qml/CompanionShellIpc.qml`) so the shell's registry dispatches to its existing `dictate` method, and falls back to `IpcHandler` (`qml/CompanionIpcHandler.qml`) on Omarchy builds where `ShellIpc` is not a type. The contract was verified against [`omarchy-shell`](https://github.com/omacom/omarchy/blob/7eedd1736d63cd7882c6479b19e1ff31f4b77c21/bin/omarchy-shell), [`IpcRegistry`](https://github.com/omacom/omarchy/blob/7eedd1736d63cd7882c6479b19e1ff31f4b77c21/shell/Commons/IpcRegistry.qml) and the socket server in `shell.qml`, introduced by Omarchy commit `c231097df7443b3fe990d6ed6e9f90b963260430` on 27 September 2026. Dictation requires a complete accepted reply within two seconds, with no retry or argv fallback after failure. Unmatched text and failed routes retain the existing filter/type fallback, with `wtype -` receiving stdin. `reply <askId>` also reads its answer from stdin and uses this private socket, rejecting oversized input. Other control-helper methods still forward to `omarchy-shell` and are outside this private dictation transport.

## Daemon backend (experimental)

`bin/agent-desktopd` (`agent_desktop/daemon.py`) is an opt-in alternative to the one-shot ask path, selected with `"backend": "daemon"` on this plugin's `shell.json` entry; the default is `"legacy"`, everything described above. It is one long-lived process per shell session, launched with `setpriv --pdeathsig TERM` and `/usr/bin/python3 -I` and the same `askEnvironment()`, that speaks newline-delimited JSON on its stdin and stdout. It holds every bot's conversation in `agent_desktop/state.py`, a pure port of the conversation logic in `Main.qml` with time injected so it can be unit-tested, and runs every ask with the existing adapter classes: GrokBot still runs `bin/grokbot-ask` per ask, and Hermes still runs through `bin/agent-desktop-provider`. A provider that streams can send text as it arrives (`ask.delta`); of the bundled adapters only Hermes declares streaming. Nothing is written to disk, so conversations still end with the process. After `hello` it serves `reply` and `dictate` on a private control socket, `$XDG_RUNTIME_DIR/agent-desktop/ctl.sock` (directory 0700, socket 0600, peer uid checked with `SO_PEERCRED`). Drafts, attachment staging and all view state stay in QML. [docs/DESKTOP-PROTOCOL.md](docs/DESKTOP-PROTOCOL.md) is the contract. The backend has unit and integration tests but has not been live-tested on an Omarchy desktop.

## Settings ownership

Position, the active bot, sync, custom shape and colour, size, dodge, and idle motion are written through `shell.updateEntryInline` onto this plugin's own `plugins[]` entry, merged with keys already there. Dispatch URL and command are read from that entry or from `~/.config/omarchy/grokbot-desktop.json` and are not rewritten by the service; `bin/grokbot-connect`, run by hand, writes only `dispatch`, `webhookUrl`, and `webhookHeader` in that file, plus the key files (at `webhookKeyFile` and `webhookHeaderFile` when those are set).

Removal of the plugin does not delete `grokbot-desktop.json`, `grokbot-bots.json`, `grokbot-webhook.key`, or `grokbot-webhook-header.key`. The service does not edit Hyprland. `grokbot-desktop-close` and `grokbot-desktop.desktop` are opt-in copies.

The local-agent transport retains the process-group leader until descendant cleanup, handles termination, and reaps it before returning. Adapter shutdown stops its local workers; cancelling a remote webhook only stops local waiting and reports that remote work may continue.

Node runs the portable checks only. It is not part of the shell plugin.

Workbench registration and command trust remain explicit user actions. Portable checks do not establish live desktop acceptance.

## Open Bot Avatar v1

`qml/openbotavatar.js` vendors the pinned MIT upstream geometry validator and frame engine. `OpenBotAvatar.qml` draws its paths and affine transforms through Qt Shapes, with no browser or runtime Node dependency. Assignments are geometry-only JSON stored under `avatarDefinitions` in this plugin's existing shell entry, keyed by desktop agent identity. Import validates before saving, export returns the normalized definition, and removal affects only that agent. The main mark, header, roster chips and reply peek use the same definition. Existing measured shapes remain the default.

## Settings navigation

`PreferencesPanel.qml` is the settings entry point: Providers, Appearance and Behaviour are separate pages in a persistent sidebar. Settings expands to a 780px card, clamped to the output; narrow views put the same categories above the content. Related controls use bordered SettingsGroup sections. `SettingsPanel.qml` retains the original shape, colour, motion and placement picker. Optional Open Bot Avatar import/export lives one level below Appearance. Provider selection uses the same `selectBot` path as the conversation picker, preserving agent-specific threads and drafts.

`HermesSettings.qml` edits only Hermes connection paths through `bin/agent-desktop-config` over stdin. The helper validates paths, preserves unrelated JSON keys, refuses symlink targets and writes atomically with private permissions. Credentials remain owned by the existing Hermes installation.

## Avatar generation

`AvatarBuilder.qml` offers describe → generate → preview → apply within the optional custom-avatar page. `bin/agent-desktop-avatar` reads Omarchy’s default agent independently of chat dispatch, resolves its installed CLI and selected account, and reuses the bounded stdin transport/process-group cleanup. It uses the pinned upstream design prompt. Requests are limited to 24 KiB, descriptions to 2,000 characters, model output to 64 KiB and compact avatar JSON to 16 KiB, with a 180-second transport deadline and UI cancellation backstop.

Generation runs in a temporary empty working directory. Claude runs with built-in tools/MCP and hooks disabled; Grok uses an empty tool allowlist and deny-all rule; Codex uses read-only sandboxing with shell/image tools, apps, web search and MCP disabled by session overrides. No credentials are copied and no model/provider is silently substituted. Supported defaults are initially Codex, Claude and Grok. CLI/account contracts were checked against Omarchy quattro `omarchy-default-agent`, `omarchy-agent-account-home`, the Claude CLI reference, Codex configuration reference, and Grok’s headless-mode documentation. Other defaults need an explicit headless adapter.

The helper returns geometry only and never writes shell settings. The QML engine validates the draft before rendering; Apply reuses import validation and storage limits, and requires the originating agent to remain selected. Drafts are in memory. Real model generation, subscription/account integration and model design quality remain live acceptance checks.

Avatar requests override Codex reasoning effort to `low` for that invocation only. The shared transport multiplexes nonblocking stdin writes with stdout/stderr reads, so startup output cannot deadlock a large prompt and the deadline includes prompt delivery. Tests cover a child that fills stderr before reading and a child that never reads stdin. The UI reports elapsed waiting time without inventing model progress.
