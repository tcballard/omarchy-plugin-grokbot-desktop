# Architecture

`Main.qml` is a `kind: service` entry point. It runs inside the long-running `omarchy-shell` Quickshell process and mounts one transparent `PanelWindow` per output on `WlrLayershell`. A layer surface stays on the output it first mapped to, so each output has its own window and only the one named by `monitor` is shown. A drag that crosses the edge keeps going: the press is cancelled by the compositor at the boundary, and `bin/grokbot-cursor` then supplies the position plus the left-button release (BTN_LEFT only, from mouse event nodes, never grabbed). The drop writes `monitor`, `marginX`, and `marginY` as integers onto the existing shell entry and does not rewrite the rest of that entry. The mark uses those same integers, so a later start puts it back on that output. The mark is placed with `marginX` and `marginY` from the corner named by `anchor` (`br`, `bl`, `tr`, or `tl`). The window always covers the whole output and never changes size or anchors. An earlier version shrank it to a box around the mark while idle, but Hyprland re-places a layer surface that grows or shrinks, so the mark visibly jumped toward the middle of the screen whenever the card opened or closed. The cost is that motion redraws the whole output's surface: in Calm, the default, that only happens while the eyes follow the pointer, while Playful and Hyper breathe continuously. Before the window first maps, the companion adds a runtime layer rule (`hyprctl eval`, `hl.layer_rule` with `no_anim` for the `grokbot-desktop` namespace), the same rule Omarchy's `apps/omarchy-shell.lua` gives its own shell surfaces, so it is not popped in from the middle of the screen when shown; it adds the rule again after each `configreloaded` event, and shows the window when that call returns or after 1.5s. The window is hidden while Omarchy's screensaver runs (`org.omarchy.screensaver`: a full-screen terminal window in older Omarchy, which the companion's top layer would otherwise draw over, and a native overlay-layer surface since 27 October 2026), tracked from Hyprland's `openwindow`/`closewindow` and `openlayer`/`closelayer` events, with a 20-second `hyprctl` check while hidden in case a close event is missed. A `mask` limits pointer input to the mark and, while it is open, the bubble card (chat and appearance pages). The rest of the desktop stays clickable with the bubble open; the minimize button, Esc, a click on the mark, or `dismiss` closes it. Only the right-click menu widens the mask to the output, so a click anywhere closes the menu.

Dodge mode, on by default, uses the cursor helper rather than the layer surface. When the pointer comes near the mark, the mask drops and the mark fades until the pointer has rested inside the mark. Calm motion keeps a slow breath and skips the float. Playful adds the float and the gaze spring. Hyper orbits and hops. Gaze spring frames run only while the eyes are catching up. Blink, ask, and named animations still run when they are triggered.

`qml/shapes.js` stores Grok Bot's fourteen avatar shapes, measured from the app's own avatar picker by `tools/measure-avatars.py`: each outline (tilt included) resampled to the same point count, the two eye capsules for that shape, and the picker's pumpkin stem for the pebble. `morphProgress` can blend any shape into any other, eyes included. `qml/palette.js` stores the 11 named colours. `qml/theme.js` holds the chrome colours for the card, menu, and name tag. Text is set like Grok Bot's app, which uses Apple's SF Pro: SF Pro Text or SF Pro where installed, otherwise the bundled Inter (`assets/fonts`, SIL OFL 1.1, Regular and SemiBold subset to Latin, Greek and Cyrillic), the closest open match. Emphasis uses SemiBold rather than Bold, as the app does, which also keeps Qt from emboldening the SemiBold face. Without either font, the shell's `Style.font.family` applies. `CompanionMark.qml` draws the silhouette as a `QtQuick.Shapes` path (the curve renderer where Qt has it) and the eyes as two rotated rounded rectangles (`MarkEye.qml`), so the mark is drawn on the GPU and stays crisp at fractional scales; only a bot photo, when one is set, is clipped through a Canvas. `qml/face.js` sizes the two eye cut-outs: rounded rectangles that are tall capsules when open and flatten into lid lines when they blink or sleep. `omarchy` is not a swatch: the shell reads `accent` from the active theme `colors.toml`, with `Commons.Color` as the fallback, and crossfades it with the same morph.

`CompanionMark.qml` fills a flat silhouette. There is no outline and no highlight. The face is two capsules placed, sized, and tilted for each shape as Grok Bot draws them, leaning with their tops to the left. On the desktop they are cut through the shape (a `MultiEffect` inverted mask over supersampled, mipmapped layers), so the wallpaper shows through as it would through the app's avatar; in the bubble and appearance page they are painted in the colour of the surface behind (`#F4F4F5` on black). On the desktop the mark moves like a head, as Grok Bot moves Bob (measured from a 60fps recording of the app's chat header): facing the pointer's direction, the eyes travel about 0.4 of the body radius across and 0.3 up or down, shrink and narrow as the face turns away (they are largest and upright facing you), and the whole outline rolls up to 20 degrees with the turn. A pointer off a corner turns it fully both ways. Bob's picker pose is his look up and to the right. Each shape's face position, eye size, and how much of each look its eyes can take before reaching its edge come from a table in `qml/shapes.js` generated by `tools/look-table.mjs`. While an ask runs, the mark plays the app's measured "Working…" loop of looks and holds, each reached in about 280ms on a fast-out curve, with one blink. The picker, roster, and header marks keep the picker pose. They squash on a blink, and squint or open for think, happy, alert, and sleep. After two minutes without a cursor event the capsules become slits. An optional `avatarImage` on a roster bot is clipped to the mark when appearance is synced from that bot. Roster shapes such as `teardrop`, `blob`, `hex`, `tablet`, `wedge`, `squircle`, `pebble`, and `cloud` are the app's own names: Grok Bot's roster shows `blob` as the round shape and `pebble` as the lumpy round one, which its picker decorates with a pumpkin stem that avatars do not wear. The remaining shapes are named for how they look, and older names alias onto the nearest of the fourteen.

Speech-bubble and settings strings that come from the roster, the prompt, a reply, or IPC use `Text.PlainText`.

## Processes

The helpers are started with a cleared environment.

- `bin/grokbot-cursor` is `/usr/bin/python3 -I -S`. It may see only `HYPRLAND_INSTANCE_SIGNATURE` and `XDG_RUNTIME_DIR`, asks Hyprland for `cursorpos`, and prints `x y` when the position changes. It also prints `down` or `up` when the combined left button changes, and no other input. It exits when its parent changes.
- `bin/grokbot-attach` is `/usr/bin/python3 -I` with only `XDG_RUNTIME_DIR`, `WAYLAND_DISPLAY`, and `HYPRLAND_INSTANCE_SIGNATURE`. `paste` reads a PNG, JPEG, WebP, or GIF image from `wl-paste`, and `file PATH...` copies files chosen in Omarchy's portal file chooser (`omarchy-file-select`, run by the shell; the card hides while it is open) or dropped on the card. Any regular file up to 25 MB is kept, under its name after a unique prefix, as a 0600 copy in `$XDG_RUNTIME_DIR/grokbot-desktop/attachments` (0700, cleared at logout, copies older than a day pruned), and each path is printed. The shell accepts only paths in that directory.
- `bin/grokbot-ask` is `/usr/bin/setpriv --pdeathsig TERM` then `/usr/bin/python3 -I`. Stdin is `{"askId","botId","botName","prompt","host","attachments"}`; up to four attachments are accepted, and only as files saved in the attachment directory. In agent mode the agent runs in that directory and the prompt names the files (Codex also gets `--image` for images); webhook mode refuses attachments. Webhook mode reads the bearer token from `~/.config/omarchy/grokbot-webhook.key` or `GROKBOT_WEBHOOK_KEY` and POSTs those four fields, with `askId` and the `replyWith` command that answers it, plus the routine's own header when `webhookHeader` names one, with its value from `grokbot-webhook-header.key`. Connecting gets 10 seconds and the answer 45; a failure names its cause on stderr. A routine that only acknowledges the ask makes it exit 10, and the shell keeps the question waiting. Agent mode resolves `grok`, `claude`, `codex`, `opencode`, and the other Omarchy agent names from trusted directories, writes the prompt to that process's stdin, and stops at 64 KiB of stdout. The token and the prompt are not arguments.

`Component.onDestruction` stops both processes. Hiding the companion cancels an ask in flight. Closing the bubble, Esc, or a click outside it does not; the Stop button in the composer does. A reply that arrives while the bubble is closed, for any bot, leaves a dot on the mark until the bubble opens; a dot for a bot whose chip is folded away shows on the header pill (`unreadHidden`). Each bot keeps its own conversation and unsent draft in memory (`threads`, keyed by bot id; never saved). A conversation is its earlier exchanges (`history`, up to 40, oldest first) plus the latest in `askedText`, `bubbleBody`, and `noticeLinks`; a new ask or notice moves the latest into the history, and the bubble shows them all in one scrolling view that settles on the newest, or on the top of a reply too long to fit. Switching bots stashes the conversation on screen and restores the next bot's. Clearing a conversation (the right-click menu or `clear` over IPC) keeps it in `clearedThread` behind an Undo chip for 8 seconds; switching bots or a new ask lets it go. One ask runs at a time; it remembers the bot it was sent to (`askBotId`), and its reply is shown if that bot is on screen or otherwise kept with it and marked with a dot on its chip (`unreadBots`). The typing dots, stop button, and work loop follow `askingHere`, which is true only while the bot on screen is the one asking.

A webhook ask that the routine only acknowledges ends the ask but not the question: `awaiting` maps its `askId` to the bot and the time, and its exchange carries the same id as `wait` (`awaitingId` for the latest on screen) through the history, bot switches, clearing, and undo. `reply <askId|bot> <text>` over IPC, or a `say` titled with a waiting bot's name, fills that exchange wherever it now is (`answerWaiting`); with nothing to fill, the answer starts a new exchange in that bot's conversation. Either way an answer for a bot not on screen marks it unread. A question still waiting after ten minutes is answered with a note that the reply will be in Grok Bot. The dots and the work loop follow `busyHere`: asking, or waiting on screen.

`bin/grokbot-connect` is run by hand, not by the shell. It reads the Webhook URL and Sender key (without echo), sends one test ask through `bin/grokbot-ask` from a private temporary copy of the settings, and only then writes the key (0600, replaced atomically) and the URL and webhook mode to `grokbot-desktop.json`, keeping its other keys.

The appearance page runs `bin/grokbot-sync --app` as an isolated Python child with only HOME and XDG_CONFIG_HOME. It reads Grok Bot's `sand-client-persistence` account-slot (schema 1) and that account's last-roster (schema 4); names are base32-encoded cache keys. It imports only profile fields, never credentials or conversation contents. Groups and removed rows are excluded. Missing, invalid, empty, duplicate, oversized, or unsupported data leaves the previous roster intact. A successful write atomically replaces `~/.config/omarchy/grokbot-bots.json`, which the service watches and explicitly reloads. `--from` still accepts a local agents directory. The cache schema is an app implementation detail; future changes fail with an actionable error.

A persistent, plain-text name badge sits below the mark, with space reserved inside the stage. It elides long names, stays within horizontal screen bounds, follows dodge opacity, and does not add an input region.

The waveform button launches `bin/grokbot-dictate`, which execs `omarchy dictation toggle` when `omarchy` is on `PATH`. That command follows `~/.config/omarchy/defaults/dictation` (`superwhisper` or `voxtype`). Without `omarchy`, the helper execs `superwhisper record` or `voxtype record toggle`. It does not take the transcript as an argument.

`qml/dictation.js` and `bin/grokbot-dictation-route` share the wake-phrase rules. `dictate` IPC and a prompt that starts with "Hey <name>" both use the QML copy. Voxtype's `[output.post_process]` filter and `bin/grokbot-dictation-route --wtype` use the Python copy so a wake phrase is not typed into the focused window. `bin/grokbot-voice-watch --enable` is the opt-in Superwhisper and Voxtype watcher. It is not started by the shell service. `bin/grokbot-desktop-ctl` forwards one IPC call to `omarchy-shell`.

## Settings ownership

Position, the active bot, sync, custom shape and colour, size, dodge, and idle motion are written through `shell.updateEntryInline` onto this plugin's own `plugins[]` entry, merged with keys already there. Dispatch URL and command are read from that entry or from `~/.config/omarchy/grokbot-desktop.json` and are not rewritten by the service; `bin/grokbot-connect`, run by hand, writes only `dispatch`, `webhookUrl`, and `webhookHeader` in that file, plus the key files.

Removal of the plugin does not delete `grokbot-desktop.json`, `grokbot-bots.json`, `grokbot-webhook.key`, or `grokbot-webhook-header.key`. The service does not edit Hyprland. `grokbot-desktop-close` and `grokbot-desktop.desktop` are opt-in copies.

Node runs the portable checks only. It is not part of the shell plugin.

Workbench registration and command trust remain explicit user actions. Portable checks do not establish live desktop acceptance.
