# Security

In agent mode, the GrokBot transport (`agent_desktop/transport.py`, run per ask as `bin/grokbot-ask`) passes the composed prompt only through the child process's stdin pipe. The Grok adapter uses `--prompt-file /dev/stdin`; no prompt text is placed in argv or the environment, and no temporary prompt file is created. Older Grok versions without this flag fail without falling back to `-p`. A user-supplied `command` also receives stdin, but that command's handling of it and the agent's own storage are outside this transport guarantee.

Optional wake-phrase routing sends the dictated text to `grokbot-desktop-ctl dictate` on stdin and then directly over Omarchy's Unix socket in the current user's private runtime directory. The helper checks the socket and peer owner and fails without an argv fallback when IPC is unavailable or its reply is incomplete. Dictation arguments are refused; scripts must pipe or redirect text into stdin. The `--wtype` fallback likewise uses `wtype -` with stdin, including after a failed route. These helpers do not copy the transcript into argv, environment variables, or temporary files. This protects against other local accounts reading process command lines, not software already running as the same user or root. Original transcripts, opt-in diagnostic output (`--check-file`, `--decide`, JSON routing), a configured diagnostic sink, and the dictation backend's own storage remain outside that transport guarantee. Direct text arguments to `omarchy-shell` or other control-helper methods remain visible in process listings.

The desktop companion reads a webhook bearer token from `~/.config/omarchy/grokbot-webhook.key` or from `GROKBOT_WEBHOOK_KEY` in the helper process. It refuses a key file that other users can read. A routine's own extra header, named in `webhookHeader`, takes its value from `~/.config/omarchy/grokbot-webhook-header.key` under the same rule; header names the helper sets itself are refused, and so is a value with control characters, so a value cannot start another header line. The token is not accepted on argv, and the shell launch does not forward `GROKBOT_WEBHOOK_KEY`. `bin/grokbot-connect` reads the key without echo, tests it before saving, writes key files mode 0600 in one step (to `webhookKeyFile` and `webhookHeaderFile` when set), and puts the earlier settings and keys back if a write fails. The `reply` IPC command, like `say`, can be called by anything that can already run `omarchy-shell` as you; it only shows text as plain text and accepts an ask id of plain hex or a bot name. Prompts go to `bin/agent-desktop-ask` on stdin, and from there to the provider adapter and its worker over pipes. Attached files are copied by `bin/grokbot-attach` into a 0700 directory under `$XDG_RUNTIME_DIR` and only paths inside it are passed on; webhook mode does not send them. When an ask fails, the bubble shows the failing helper's own one-line reason: for a local agent, what that agent printed on stderr; for a webhook, its status and error message. The text is shown as plain text, with control characters removed and at most 400 characters, and a Python traceback from the GrokBot worker is replaced by a generic message. An agent that prints a secret in its error output will therefore have it shown on screen.

The optional daemon backend (`bin/agent-desktopd`, experimental and off by default) listens on `$XDG_RUNTIME_DIR/agent-desktop/ctl.sock` for `reply` and `dictate`. It serves only when `XDG_RUNTIME_DIR` is owned by the user with no group or other access; the `agent-desktop` directory is 0700 and the socket 0600, and each connection's peer must have the daemon's uid (`SO_PEERCRED`). Requests are bounded (64 KiB, read within 2 seconds) and text travels in the request body, not in argv. `bin/grokbot-desktop-ctl` applies the same checks before sending, and falls back to Omarchy's shell socket only when the daemon socket is absent or refuses the connection. Like the shell socket, this protects against other local accounts, not software already running as the same user.
