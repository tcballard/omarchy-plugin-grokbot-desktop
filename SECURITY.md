# Security

In agent mode, `bin/grokbot-ask` passes the composed prompt only through the child process's stdin pipe. The Grok adapter uses `--prompt-file /dev/stdin`; no prompt text is placed in argv or the environment, and no temporary prompt file is created. Older Grok versions without this flag fail without falling back to `-p`. A user-supplied `command` also receives stdin, but that command's handling of it and the agent's own storage are outside this transport guarantee.

The desktop companion reads a webhook bearer token from `~/.config/omarchy/grokbot-webhook.key` or from `GROKBOT_WEBHOOK_KEY` in the helper process. It refuses a key file that other users can read. A routine's own extra header, named in `webhookHeader`, takes its value from `~/.config/omarchy/grokbot-webhook-header.key` under the same rule; header names the helper sets itself are refused, and so is a value with control characters, so a value cannot start another header line. The token is not accepted on argv, and the shell launch does not forward `GROKBOT_WEBHOOK_KEY`. `bin/grokbot-connect` reads the key without echo, tests it before saving, and writes key files mode 0600 in one step. The `reply` IPC command, like `say`, can be called by anything that can already run `omarchy-shell` as you; it only shows text as plain text and accepts an ask id of plain hex or a bot name. Prompts go to `bin/grokbot-ask` on stdin. Attached files are copied by `bin/grokbot-attach` into a 0700 directory under `$XDG_RUNTIME_DIR` and only paths inside it are passed on; webhook mode does not send them. Do not post credentials or sensitive exploit details in a public issue. Use GitHub private vulnerability reporting if enabled; otherwise ask the maintainer for a private reporting channel before sending sensitive details. No response-time commitment is implied.
